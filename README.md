# humAIn — запускаемое Django-приложение

Форум об ИИ: публичное чтение, регистрация, обсуждения с тегами, сообщения,
поиск, модерация, смена логина/пароля с отзывом сессий и история с восстановлением.
Исходные документы проекта оставлены без изменений.

## Быстрый локальный запуск

Команды выполняются **в корне репозитория `RBPOrepo`**, а не в родительской папке `RBPO`.
Нужен Python 3.12–3.14. Реализация проверяется на Python 3.14, Django 5.2.17.

```sh
cd /Users/42na/RBPO/RBPOrepo
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py migrate
.venv/bin/python manage.py runserver 127.0.0.1:8000
```

Открыть <http://127.0.0.1:8000/>. Проверка:

```sh
curl --fail http://127.0.0.1:8000/health/
```

Ожидается `{"status": "ok", "service": "humAIn"}`. Endpoint также обращается к БД.
SQLite создаётся автоматически в `db.sqlite3`; данные сохраняются после перезапуска.
В этой рабочей копии виртуальное окружение и миграции уже подготовлены.

## Первое обсуждение

1. Зарегистрировать пользователя через `/register/`.
2. Назначить ему роль модератора доверенной серверной командой:

   ```sh
   .venv/bin/python manage.py set_moderator ИМЯ_ПОЛЬЗОВАТЕЛЯ
   ```

3. Войти заново: смена роли отзывает старые сессии. На странице `/tags/` создать тег.
4. Создать обсуждение с этим тегом. Другой зарегистрированный участник может ответить.
5. Гость может читать и искать. Участник удаляет своё, модератор — своё и контент участников.

Готовых аккаунтов и общих паролей нет. Суперпользователь не получает скрытого обхода
правил форума; модераторство задаётся отдельно. Веб-панель `/admin/` позволяет
просматривать пользователей, контент и историю. Создание, изменение и удаление
через неё запрещены даже суперпользователю: операции контента выполняются через форум.
Вход и смена пароля используют существующие защищённые маршруты форума.
Назначение существующего аккаунта администратором и модератором без смены пароля:
`manage.py set_admin ИМЯ --seed-tags`. Дополнительный флаг создаёт пять начальных
тегов только при отсутствии тегов, с обычной историей изменений. Требуется повторный вход.
Для отзыва роли: `manage.py set_moderator ИМЯ --revoke`.

## Docker + PostgreSQL

Нужны работающий Docker Desktop / Engine и Compose. Создать локальный `.env`
(не включать в Git; в данной рабочей копии он уже создан со случайными значениями):

```sh
python3 - <<'PY'
from pathlib import Path
import secrets
p = Path('.env')
if not p.exists():
    p.write_text('POSTGRES_PASSWORD=' + secrets.token_urlsafe(32) + '\n'
                 'DJANGO_SECRET_KEY=' + secrets.token_urlsafe(64) + '\n')
    p.chmod(0o600)
PY
docker compose up --build -d
docker compose exec web python manage.py set_moderator ИМЯ_ПОЛЬЗОВАТЕЛЯ
```

Приложение доступно на <http://127.0.0.1:8000/>; PostgreSQL не публикует порт наружу.
Миграции выполняются при запуске. База хранится в Docker volume `postgres_data`.
Остановка без удаления данных: `docker compose down`.
SQLite и PostgreSQL — две независимые базы: регистрация в одной не создаёт аккаунт в другой.
Не запускайте оба варианта одновременно на порту 8000.

Compose предназначен для локальной демонстрации (`DEBUG=1`, Django runserver).
Для публичного размещения нужны отдельная конфигурация WSGI-сервера, HTTPS и раздача static.
При `DJANGO_DEBUG=0` обязательны `DJANGO_SECRET_KEY` и `POSTGRES_HOST`; включаются
HTTPS redirect, Secure cookies, HSTS. TLS должен завершаться непосредственно перед
приложением; доверие заголовкам proxy по умолчанию не включено.
`DJANGO_ALLOWED_HOSTS` — список хостов через запятую.

## Проверки

```sh
.venv/bin/python manage.py check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test --verbosity 2
docker compose exec web python manage.py test --verbosity 2
```

SQLite запускает функциональные проверки; четыре теста конкурентных транзакций
явно пропускаются. PostgreSQL запускает весь набор, включая два одновременных
изменения учётных данных, вход одновременно со сменой пароля, удаление двух
последних тегов и согласованность истории при параллельных записях.
MD5 применяется только внутри тестов для скорости. Рабочие пароли хешируются
стандартным PBKDF2 Django с солью.

## Восстановление контента (SR-7)

Каждое создание/удаление обсуждения, сообщения или тега сохраняет полное состояние
контента до и после операции в той же транзакции. Отказанные операции историю не меняют.

```sh
.venv/bin/python manage.py content_history
.venv/bin/python manage.py restore_content 12 --side before --confirm
```

В Docker замените `.venv/bin/python` на `docker compose exec web python`.
Команда восстанавливает **весь контент форума**, а не только один объект.
Перед откатом изучите номер операции. Сам откат добавляет новую ревизию, поэтому
его тоже можно отменить. Восстанавливаются ID, авторы, даты, тексты, теги и связи.
Учётные данные, роли и сессии не откатываются. Веб-доступа к истории/откату нет;
команда доступна доверенному оператору сервера.

История не заменяет резервное копирование БД и не защищает от администратора БД.
Полные снимки и общая блокировка подходят для небольшого учебного форума:
объём истории растёт с количеством контента и операций; записи сериализованы.

## Принятые уточнения

- Удаление обсуждения запрещено, если оно каскадно удалит сообщение другого
  модератора. Это правило подтверждено пользователем при реализации.
- Последний тег любого обсуждения удалить нельзя. Изменение содержания/тегов
  уже созданного обсуждения отсутствует, как и другие операции редактирования.
- Поиск использует объединение выбранных тегов (хотя бы одно совпадение).
  Главный ключ — число разных совпавших тегов. Далее `(число сообщений + 1) /
  (возраст в часах + 2)`, затем дата и ID. Без фильтра показаны все обсуждения.
- Топ-3 сортируется по числу сообщений, затем по дате и ID.
- Дата события для обратного отсчёта в исходных документах не задана. Задайте
  `COUNTDOWN_TARGET=2030-01-01T00:00:00+03:00` (пример даты); без настройки блок скрыт.
  Это необязательная функция по паспорту.
- Автор берётся только из сессии; дополнительные поля автора, роли или аккаунта
  в POST отклоняются. Все изменения выполняются POST с CSRF.
