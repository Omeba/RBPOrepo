### D-03. Изменение собственных данных авторизации с отзывом сессий

**Контекст:** участник и модератор должны иметь возможность изменить логин и пароль своего аккаунта (SR-5). При угрозе T-2 злоумышленник получает данные модератора и может удалять контент от его лица. Смена пароля запрещает вход по старым данным, но сама по себе не прекращает доступ через сессию из D-01, которая может действовать до 7 дней.

**Решение:** разрешить изменение собственных данных авторизации через сервер приложения.

1. Пользователь отправляет по HTTPS текущий пароль и новый логин и/или пароль. Сервер определяет аккаунт по сессии из [D-01](D-01.md). Запрос изменения чужого аккаунта отклоняется, в том числе для модератора.
2. У аккаунта хранится версия данных авторизации, а у сессии - версия на момент входа. Логин, хеш пароля и версия обновляются в одной транзакции с блокировкой записи пользователя. Текущий пароль и версия сессии проверяются после получения блокировки. Если два запроса используют прежнюю версию, успешно завершается только первый.
3. При каждом защищённом запросе сервер сравнивает версии аккаунта и сессии. После смены данных все прежние сессии, включая текущую, перестают давать доступ; пользователь входит заново. При входе проверка пароля и чтение версии выполняются под той же блокировкой: одновременная смена пароля не должна позволить выдать сессию новой версии по старому паролю.

**Обоснование:** сессия определяет, чей аккаунт можно изменить, а текущий пароль защищает от смены данных при краже одной лишь сессии. Проверки на сервере работают и в обход интерфейса. Транзакция исключает частичное обновление данных, а смена версии отзывает старые сессии без ожидания их истечения.

**Альтернатива:** сохранять сессии после смены данных, чтобы пользователю не приходилось входить заново. Вариант отклонён: сессия злоумышленника тоже продолжит работать. Его можно пересмотреть при появлении управления отдельными сессиями с обязательным отзывом остальных и заменой текущей.

**Связанные угрозы:** [T-2](../THREAT_MODEL.md).

**Связанные требования:** [SR-5](../SECURITY-REQUIREMENTS.md). Решение дополняет D-01.

**Предположения:** пользователь имеет доступ к аккаунту и знает текущий пароль. Все пути входа и защищённые операции должны проверять актуальную версию аккаунта из БД.

**Будущая проверка:** после реализации проверить критерий требования безопасности SR-5 и работу выбранного механизма:

- Участник и модератор меняют собственный логин, пароль или оба значения -> вход по новой паре данных успешен, по прежней отклоняется; роль и авторство контента сохраняются.
- Пользователь отправляет прямой запрос для чужого аккаунта, с неверным текущим паролем, некорректным CSRF-токеном или занятым логином -> отказ без изменения данных и отзыва действительных сессий.
- У модератора открыты две сессии; из первой он меняет данные -> обе прежние сессии больше не позволяют удалить сообщение участника, сообщение сохраняется; после нового входа операция доступна.
- Одновременно отправляются два запроса смены данных либо вход по старому паролю и смена пароля -> второй запрос смены отклоняется; вход по старому паролю не выдаёт сессию, действительную после смены.
- Обновление прерывается до фиксации транзакции -> логин, хеш пароля и версия остаются прежними.

**Ограничения и последствия:**

- После смены данных нужен повторный вход на всех устройствах. Сервер должен хранить версию аккаунта и проверять её при каждом защищённом запросе.
- Злоумышленник, знающий текущий пароль, может сменить данные раньше владельца. Восстановление доступа и дополнительные факторы аутентификации требуют отдельного решения.
- Смена данных не предотвращает их повторную кражу и не восстанавливает удалённый контент. Операция, прошедшая проверку доступа до смены данных, может завершиться.
